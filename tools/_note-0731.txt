本版两张卡 + 一张对抗验收（Mod 无源码改动，只 bump 版本号）：

1. task-143（dev-coder）播种分配额 = 手上种子数：
   - `_stage_tiles("plant_area")` 的上限改为 `limit = min(self.per_stage_tiles, seeds_total)`；
   - run9c 实证：day1 两条 stage 记录 `assigned 12 / ok 11 / undone 1 / stopped "no_seed"` 与 `assigned 4 / ok 1 / undone 3 / stopped "no_seed"` —— 手上只有 11 粒却分了 16 格，多出来的格既做不成也不算"没活"⇒ `checks.no_unmet_stages=false`；
   - **不许**把 `no_seed` 塞进"诚实上限"白名单（买不到种子 ≠ 今天该做的活做完了）。

2. task-144（dev-coder）浇水阶段壶空必须补水续做：
   - `water_area` 阶段内壶空（`water()` 返回 `need_refill`，或阶段开始前 `waterLeft == 0`）⇒ 先 `refill_can()`（每阶段/每天有界 ≤2 次）再继续浇，把分下去的格做完 ⇒ `assigned_undone` 归 0；
   - 补水不可能（无补水点/失败/达上限）⇒ 保持诚实：`stopped="need_refill"` + `assigned_undone` 照旧计入 unmet（**不许**洗白）；
   - 消除 `stopped == ""` 却 `assigned_undone > 0` 的形态（run9c：`assigned 21 / undone 3 / stopped ""`）——正常结束不许有格没做且不解释；
   - run9c 实证：`water_area assigned 70 / undone 27 / stopped "need_refill"`（壶容 40），而补水链本身可用（当天有 `refill 0→40`）。

3. task-145（deputy-lead，对抗验收）0.7.31 批次：A 段范围/读数；B 段复现 run9c 两条形态 FAIL→PASS；C 段 ≥6 组对抗（重点打"新洗白通道"：壶空被写成够不着/诚实上限、分配额上限被用来掩盖真未完成、`stopped==""` 与 `assigned_undone>0` 并存、补水自旋、买不到种子被当成收工理由）。
