## 1. `PreCheck / Execute / PostCheck` 三段契约

**出处**：`src/AutoFarmWorker/ModEntry.ActionExec.cs:60-229`（`PreCheckFor` :60-156、`PostCheckFor` :182-229）；执行段 `BuildTaskFor` :236-297；白名单 :42-47。

### 1.1 模式是什么

每个动作原语**自带三段**：

| 段 | 语义 | 关键约定 |
|---|---|---|
| `PreCheck` | "现在能不能做" | 返回非 null = **跳过**（**不算失败、不报错**） |
| `Execute` | 真正的世界操作 | 见 §1.3 |
| `PostCheck` | "做成了没有" | 判据取自**世界状态**，不取解决策方自述 |

### 1.2 好在哪（有真实故障对应）

- **决策方会给出"看起来合理但当前做不了"的动作**。作者在 `ActionExec.cs:24-33` 把三类列了出来：对已种上的地再 `plant`、只有基础斧时 `remove_stump`、种子用完还继续 `plant`。**如果靠决策方自己保证，它只要错一次，整条链路就空转。**
- **"跳过"与"失败"被刻意分开**。"树桩但斧头不够"是**世界约束**，不是错误 —— 判为跳过就不会污染失败计数、不会触发安全自救，也不会在日志里制造噪声。这个区分是**正确的语义分层**（对照 §5 缺陷 D1：结果语义缺失正是旧项目最大架构缺陷，而 `PreCheck` 这一层反而做对了）。
- **`PostCheck` 把"成功"变成硬事实**。`ActionExec.cs:178-181` 的注释写得很准："判据来自**世界状态**，不是决策方的说法 —— 这样'计划执行成功与否'是硬事实。" 具体判据很干净：收获成功 = `dirt.crop == null`（作物被收走了）；清障成功 = `obj == null`；浇水成功 = `!needsWatering()`。审计 §1.2(d) 把这一点单列为**好设计**并要求新项目保留。
- **白名单是防幻觉硬闸门**。`ActionExec.cs:36-37`："表外的名字一律拒绝并记日志 —— 决策方就算胡说，最坏结果也只是'这条被丢弃'，不会让角色执行不存在的操作。"

### 1.3 唯一的重大缺口：`Execute` 段没有副作用校验

`water`/`clear_*`/`break_stone`/`scythe_or_till` 全部**直接改数据**（`ActionExec.cs:321-504`），不是模拟输入。其中 `break_stone` 直接 `objects.Remove` **不会掉石头/矿石/晶球**（审计 §2.2）。

### 1.4 我们怎么用

1. **保留三段结构**，但把 `Execute` 升级为"**必须走真实工具路径**"：能用 `Tool.DoFunction` 的（砍树/树桩/灌木/翻地/浇水）一律走 `DoFunction`；只有收获走 `Crop.harvest` 反射（见 API 页 §2.1）。
2. **`PostCheck` 判据只读世界状态**，并把结果写成结构化 `ResultKind`：`done` / `no_effect` / `blocked_by:<capability>` / `failed`。**不要**再压成一个 `skipped` 桶（这正是 §5 D1）。
3. **`PreCheck` 的"跳过原因"必须机器可读**。旧项目把中文原因直接写进 `ai_result.json`（`ModEntry.Ai.cs:541`），导致"跨地点退避中"这个**能力缺失**被伪装成一条普通跳过理由，最终没人发现"根本到不了农场"。新项目：`PreCheck` 返回 `(code, human_reason)`。
4. **把"白名单"升级为"能力注册表"**。旧项目的白名单有两份硬编码且靠手工同步（`LegalActions` @ `ActionExec.cs:42-47` vs Python 侧 `LEGAL` @ `ai_planner.py:428-430`）= 审计缺陷 D5。新项目：白名单**从一个源生成**，且把 `PreCheck`/`PostCheck` 一起注册进去，避免"动作存在但没人检查"。

## 2. `SelfTest()` 自检模式 —— 专治"字段静默丢失"

**出处**：`src/AutoFarmWorker/AiDirective.cs:204-260`（自检本体）；`[JsonProperty]` 显式标注 :45-127；宽松时间解析 :292-314。

### 2.1 模式是什么

拿一段**含全部字段**的 JSON 字面量，走一遍**真正的反序列化**，然后**逐字段核对**是否绑定成功；缺失字段收集成列表返回；调用方在 **Mod 初始化时跑一次**，失败就明确报错。

具体到实现（`AiDirective.cs:227-249`）：对每个字段做 `if (d.Xxx == null) missing.Add("xxx")`；连嵌套的 `plan[0]` 也核（`.Action`/`.Xy`/`.Id`），并且**核对值**（`it.X != 1 || it.Y != 2` → "plan[].xy 值不对"）。

### 2.2 好在哪（有真实故障对应）

作者在 `AiDirective.cs:196-199` 写下了动机：

> 实测踩过的坑：`expires_at` 因为命名风格不匹配而**静默丢失**，导致"过期安全阀"完全失效，而且不报错、不告警。这类问题的共同特征是"看起来一切正常" —— 只能靠自检暴露。

这是**整份文档里最有价值的一条经验**：SMAPI 的 `ReadJsonFile` 不做 snake_case→PascalCase 转换但大小写不敏感，所以 `expires_at`/`plan_basis`/`issued_at` **静默丢失**，而单词字段（`goal`/`reason`/`mode`/`plan`）**不受影响** —— 于是"部分字段正常"让整个系统看起来是好的。

**它为什么是"模式"而不是"补丁"**：反序列化的静默失败**没有任何运行期信号**。唯一能提前发现的手段就是"构造全覆盖输入 → 断言全覆盖输出"。这个思路与具体字段无关，可以套到任何契约面上。

### 2.3 我们怎么用

1. **自检必须覆盖所有契约面，不只指令**：指令、快照、结果、配置、白名单、数据表（`crops.json`）各来一份。
2. **自检要在启动时跑，失败即 Error**。旧项目的 `SelfTest()` 存在，但 `ExpectedSchema` 从未参与校验（只在生成示例文本时被打印，`ModEntry.Ai.cs:678,759`）= 审计缺陷 D5。**有自检机制但没接上闸门，等于没有。**
3. **自检要包含"值"而不只是"非 null"**。旧项目核了 `plan[].xy == [1,2]`，这一步很关键 —— 它能抓到"字段绑上了但类型/结构被误解"的情况。
4. **对 fail-closed 的字段（安全阀）额外做"语义自检"**：写一个空串进去，断言它**被判为过期**。旧项目恰好相反（`IsExpired` 解析失败 `return false`，`AiDirective.cs:143-145`）。

## 3. `SurroundingsSnapshot` 逐字段 `try/catch` 容错

**出处**：`src/AutoFarmPlanner/SurroundingsSnapshot.cs:33-629`（快照主体），写盘 :54/:69，容错约定 :26-28，`Summarize()` 供人读。

### 3.1 模式是什么

快照由**几十个独立字段**组成（`save` / `player` / `location` / `farm` / `mine` / `signals`），**每一个字段各自 `try/catch`**。某个 API 变了、某个字段取不到、某次调用抛异常 —— **只丢那一个字段**，其余照常输出。另有一个 `Summarize()` 把同一份数据渲染成人读摘要。

### 3.2 好在哪

- **故障半径从"整份快照"缩到"一个数字"**。游戏更新或边界情况只会让一个字段变空，而不会让整个感知层停摆。审计 §1.2(b) 直接评定为**工程质量全项目最高**。
- **它是"读"侧的正确姿态**。写侧改坏了世界无法挽回，读侧读不到只是这一个判断降级 —— 所以容错应该集中在读侧。
- **`Summarize()` 是隐藏价值**：同一份数据既有机器格式又有人读格式，排障时不用写额外的解析脚本。

### 3.3 局限（要看清楚）

- **审计同时指出：AI 规划器根本不读这份快照**。真正的感知输入是 `farm_tiles.json`（`ai_planner.py:58`；审计 §1.1）。也就是说这个"工程质量最高的组件"**在生产链路上是旁路**，消费方只有 `state_report.py` 等工具。
- **逐字段 `try/catch` 会掩盖"该字段永远取不到"**。旧项目的 `farm_entry_xy` 实测**恒为 `[64,15]` 硬编码兜底**（审计 §0），而快照层一直"正常输出"这个字段 —— 容错机制让一个持续性缺陷伪装成了健康状态。

### 3.4 我们怎么用

1. **保留逐字段容错**，但**加一层"字段健康度"记账**：每个字段记录 `ok` / `missing` / `threw`，并在**同一字段连续 N 次异常时升级为 Error**。这样既不因一个字段炸掉整份快照，也不让持续性缺陷永久隐身。
2. **禁止静默兜底值**。`farm_entry_xy` 的教训：取不到时应该输出 `null` + `"unavailable"`，而不是填一个硬编码坐标让上游以为拿到了真值。
3. **保留 `Summarize()`**，并且**让摘要里显式标注降级字段**（"以下字段本帧不可用：…"）。
4. **把"世界是否在推进"这类**活性**字段作为一等公民**（见 §4），而不是普通字段。

## 4. `WorldIsAdvancing` / `TickLiveness` 活性检测

**出处**：`src/AutoFarmWorker/ModEntry.TileMap.cs:58-110`（`TickLiveness` :58-73、`SecondsSinceGameClockMoved` :76-77、`WorldIsAdvancing` :85-89、`LivenessJson` :91-110）；相关：`ModEntry.FocusPause.cs:27-151`（`FocusPauseEnsure`）、`ModEntry.CheckWorldStall`。

### 4.1 模式是什么

每 Tick 记下 `Game1.timeOfDay` 与 `Game1.dayOfMonth`；两者任一变化就刷新 `_liveLastChangeAt`。由此派生：

- `SecondsSinceGameClockMoved` = 距上次时钟变化的秒数；
- `WorldIsAdvancing()` = `Context.IsWorldReady && SecondsSinceGameClockMoved < 20.0`；
- **把它写进快照**：`liveness.{world_advancing, game_time, day, seconds_since_clock_moved, warning}`；停摆时额外写一条警告文本：
  "游戏内时钟已停摆 —— 世界没有在推进（常见原因：游戏窗口失焦自动暂停）。**此状态下的所有数据都是冻结的，不要据此规划行动。**"

阈值 20 秒的取法也有依据（`TileMap.cs:82-83`）：游戏内每 10 分钟（≈现实 7 秒）tick 一次时钟，所以 20 秒没动就一定不正常；同时要排除"刚启动/正在载入"的窗口。

### 4.2 好在哪（这是全项目最有洞察力的发现）

- **它把"世界在不在动"提升成了与"世界是什么样"并列的一等事实**。绝大多数自动化系统的假设是"我读到的就是现在"；这个项目发现了该假设会失效的**具体机制**：`Options.pauseWhenOutOfFocus` 在界面里**没有对应文本**（实测扫遍 Content 下 3560 个文件），但 `Game1._update` **仍在读它** —— 一旦为开，窗口失焦时世界冻结，而**快照看起来完全正常**（体力满、作物待浇、时间 8:10），实际是几十秒前的画面。
- **正确的修复姿态是"给上游一个否决依据"，不是"悄悄修好自己"**。旧项目做了两件对的事：① 主动反射关掉该选项（`FocusPause.cs:40-62`，且启动/读档/换天各调一次，因为游戏可能从配置重读）；② **同时**把活性写进快照，让上游能拒绝规划。防御纵深，而不是单点。
- **`warning` 文本直接写给"消费方"看**（"不要据此规划行动"），这条消息是给人也是给模型看的 —— 方向上很对。

### 4.3 局限

`WorldIsAdvancing` 只能证明"时钟在动"，**不能证明"任务在推进"**。旧项目在这一点上栽了最大的跟头：`IdleIsLegitimate()` 用"**队列非空**"当作"有进展"的同义词（`ModEntry.Diagnostics.cs:192`），而退避期间队列里始终挂着 39 条任务 ⇒ 看门狗认为"一切正常"，永不升级（审计 §3.2）。

### 4.4 我们怎么用

1. **活性必须是一等字段**，任何数据消费前先检查它。**数据新鲜度与数据内容分开建模**。
2. **保留"主动关闭失焦暂停"**，但**不要把它当成唯一防线** —— 新版本可能改字段可访问性或行为（旧项目就用了反射而非直接字段访问，理由写在 `FocusPause.cs:42-44`："这个字段的可访问性跨版本变过"）。
3. **把活性的粒度做细**：不止"世界在动"，还要有"**任务在推进**"。定义 `Progress` = `done > 0` **或**世界状态指纹变化。**绝不能**用"队列非空"或"计划已处理完"当进展（这两个代理量在本项目里全部失效）。
4. **`warning` 走结构化字段 + 人读文本双写**，并让上层能据此**拒绝对该帧做任何规划**。

## 5. 旧方案失败教训 —— 这些机制以后**绝对不要重做**

> 依据：`_legacy-audit.md` §2.4、§3.2、§3.3、§5。以下每一条都对应**实测故障**，不是审美偏好。

### 5.1 ❌ 全局退避标量（`_crossLocBackoffUntil`）

- **它是什么**：一个 `DateTime` 字段（`ModEntry.cs:89`），跨地点失败连击 ≥3 时置为 `UtcNow + 30s`（`:456-459`），期间**每一条**农场任务在 `:641-645` 被无条件 `DiscardTask`；入口 `:1105-1112` 还有**第二处完全相同的闸门**；`_crossLocFailStreak` **全局累计、不随换任务清零**（`:454`）。
- **为什么绝不能重做**：它把"从 FarmHouse 到 Farm **这一条路**走不通"泛化成了"**所有**跨地点工作停摆 30 秒"。而玩家位置与任务目标在这 30 秒内都没变 ⇒ 退避解除后必然再次失败、再次点亮 ⇒ **不会自愈的循环**。更糟的是清除点只有三处（超时分支重置后**立刻重新点亮**，等效于永不解除；看门狗软复位；`afw` 命令）。
- **实测后果**：39 条计划在 **0.6 秒内**全部"处理完毕"（`done=0 / skipped=39 / elapsed_seconds=0.6`，审计 §0），理由是同一句"跨地点退避中"。
- **正确替代**：退避必须是**按(起点,终点)对或按具体边**的，并且**要有过期与重新探测策略**。缺的是抽象（§5.4），不是参数。

### 5.2 ❌ 把"路径不可达"降级成"逐条跳过"（`DiscardTask`）

- **它是什么**：跨地点失败走 `DiscardTask`（`ModEntry.cs:664-675`）而不是 `PopTask(failed:true)`；前者只调 `AiNoteSkipped` 写一条备注后取下一队列首。
- **为什么绝不能重做**：① 不计入 `_giveUpStreak`（所以 8 次阈值的安全自救**永不触发**，`:670-671` 注释自己承认）；② 不停留在任何可观察的失败状态，只在 `ai_result.json` 里留一行中文；③ 与"计划能收尾"的修复（`AiNoteSkipped` 计入 `_aiPlanFinished`，`ModEntry.Ai.cs:539-544`）叠加后，**"全量丢弃"被当成了"圆满完成"**，形成正反馈空转 —— 规划器每 25~40 秒烧一次 API 重新生成一份同样会被丢弃的计划（`planner.log:1685/1720/1757` 连续三次"上一轮计划已跑完"，而农场指纹逐轮完全一致）。
- **作者自己知道**：`ModEntry.cs:650-663` 的注释记录了历史事故"角色被带进矿洞后，AI 计划 39 条被逐条丢弃却永不收尾"。
- **正确替代**：失败必须**分类且可观察**，必须指名**缺哪个能力**（`blocked_by:<capability>`），并且**只有 `done>0` 或世界指纹变化才算"跑完"**。

### 5.3 ❌ 用"队列非空"当"有进展"（`IdleIsLegitimate()`）

- **它是什么**：`ModEntry.Diagnostics.cs:188-199`，第一句 `if (this._pending.Count > 0) return true;`。看门狗在 `Watchdog.cs:167-172` 调它，返回 `true` 就刷新 `_wdLastProgressAt` 并 `return` —— **永不升级**。
- **为什么绝不能重做（这一条最值得反复读）**：该函数的 XML 注释（`Diagnostics.cs:180-187`）明确写着它**就是为了"不再被死锁骗过"**而替换掉旧的 `_planHadWork`。它把"队列非空"当成了"有进展"的同义词，于是**换了一个同样会被骗过的判据**。审计 §3.2 的评语是全文最锋利的一句：
  > 这是一个典型的"缺抽象导致的补丁"——它试图用更聪明的启发式修补一个本应由**显式进度/健康状态**回答的问题。
- **正确替代**：**不要再用启发式回答"我是否卡住"**。要有一个显式的进度状态机：`done` 计数、世界指纹、能力可用性、上次成功动作时间。判据来自这些**硬事实**，而不是"某个容器非空"。
- **元教训**：一个"更聪明的启发式"用来替换一个坏启发式，**不会**带来正确性 —— 只会带来一个新的失效模式。

### 5.4 ❌ 缺"可达性/位置"抽象，用 8 处补丁凑（缺陷 D2）

- **它们是什么**：移动逻辑散落在 `BeginCrossLocation`（`:1105-1172`）、`TryWalkToLocation`（`:1191-1284`）、`FindWarpTiles`（`:1302-1345`）、`CollectExitCandidates`（`:1356-1488`）、`FindSafeLanding`（`:1550-1572`）、`ShiftOffWarpTile`（`:1578-1600`）、`ResolveNavTarget`（`:904`）、`IsStandable`（`:947`）**八处**。
- **为什么绝不能重做**：**没有任何一处能回答"当前位置 P 能否到达地点 L"这个单一问题**，也没有状态缓存。后果是 39 个动作各自独立重试 39 次同样的失败，而没有任何一层能说"**当前无法离开 FarmHouse，别再下发农场任务了**"。
- **具体症状**：`TryWalkToLocation` 从 5 个来源并集猜出口（`CollectExitCandidates`）；`FindSafeLanding` 依赖 `target.warps` 反查落点，实测取不到 ⇒ 瞬移兜底**完全跳过**（`:1265-1281`）；12 秒等待超时是**从 6 秒放宽的调参**（`:445-446` 注释自承），而不是**判定**。
- **正确替代**：**移动必须是一等能力**（有自己的状态机、失败分类、可重试、成功后会被记住）；地点间用**显式入口/出口图**；可达性查询**可缓存且带失效条件**。

### 5.5 ❌ 缺"地点拓扑"抽象，用硬编码坐标兜底（缺陷 D3）

- **它是什么**：`WatchdogFindFarmLanding()`（`Watchdog.cs:337-372`）三层兜底，其中**分支 1 与分支 2 是逐字重复的同一段代码**（`:345-352` vs `:359-366`，只有 `farm0/v0` 与 `farm/v` 变量名不同），最终 `return new Point(64, 15)`。
- **为什么绝不能重做**：实测 `farm_tiles.json.save.farm_entry_xy` **正好是 `[64,15]`** ⇒ 前两层全部返回无效值，模型 prompt 里的"出口坐标"是**硬编码常量而非真实拓扑**（模型据此推理"出屋即落在 [64,15]"，`planner.log:1657`）。**静默兜底把一个持续性缺陷伪装成了正常数据**，这是它最有害的地方。
- **正确替代**：建立地点拓扑表（地点、入口格、出口格、触发方式），用游戏权威 API 一次性解析并缓存 —— **禁止硬编码坐标，取不到时必须显式报错**。

### 5.6 ❌ 双头决策 / 配置关闭代替物理删除（缺陷 D4）

- **它是什么**：`PlanWork()`（规则大脑，`ModEntry.cs:1637`）与 `AiLoadPlan()`（模型大脑，`ModEntry.Ai.cs:367`）两套大脑并存，`CodePlannerEnabled=false` 让规则大脑在 `:1656-1661` 直接 `return`。
- **为什么绝不能重做**：只被规则大脑调用的代码**全部失效，但没有任何机制指出它们已死**：
  - 目标格黑名单 `_blockedTiles` 的唯一消费点在 `:1745`（`PlanWork` 内）⇒ AI 路径下**完全无效**；
  - `AiFilterCandidates`（focus/avoid 过滤）同样只在 `PlanWork` 里被调用（`:1749`）⇒ **`focus`/`avoid` 两个指令字段也是死的**；
  - `_planHadWork` 在两条路径下语义相反（`:1761` vs `:1643` vs `:1658`）。
- **正确替代**：**只保留一个决策源**；任何被禁用的能力**必须物理删除**，而不是留在配置后面。"配置关闭"不等于"代码移除" —— 这在架构重写时是最危险的陷阱，因为**读者无法分辨哪些逻辑仍然活着**。

### 5.7 ❌ 靠手工同步的多份契约（缺陷 D5）

- **四处独立漂移**：① `ExpectedSchema` 声明了 `/1` 而 Python 写 `/2`，且 `ExpectedSchema` **从未参与校验**；② 动作白名单两份硬编码，靠手工同步；③ `expires_at` 安全阀两端各宽松一半 ⇒ 永久失效；④ 规划器读 `knowledge/crops.md`/`tools.md` 而目录下**只有 `strategy.md`** ⇒ 注入占位文本，`crop_economics.json` 那 11 KB 经济学数据**从未进入 prompt**。
- **为什么绝不能重做**：四处漂移**全部静默失败**，没有一处会报错。
- **正确替代**：schema 用**文件**定义，两端**强制**校验（版本 + 必填 + 枚举）；白名单**从一个源生成**；**契约漂移必须在启动时以 Error 级别失败**（把 §2 的 `SelfTest` 思路扩展到所有契约面）。

### 5.8 ❌ 全部写盘用裸 `File.WriteAllText`，没有原子写

- **它是什么**：`TileMap.cs:460`、`Ai.cs:508`、`Ai.cs:676`、`Watchdog.cs:528`、`SurroundingsSnapshot.cs:69`、`Knowledge.cs:58,121` —— 全是裸覆盖写；grep `.tmp`/`File.Replace`/`File.Move` **零命中**；无文件锁（除 Python↔Python 的 `msvcrt` 单实例锁）、无版本号/世代号、C# 侧读指令**无任何新鲜度校验**。
- **为什么绝不能重做**：Python 直接覆写 5458 B 的 `ai_directive.json` 而 Worker 每 20 秒轮询，撞上的概率不高但非零；一旦撞上，Worker 只 Warn 一行并沿用上一版 —— **表现是"计划没被执行，但日志里只有一行 Warn"**。这类"静默降级"是本项目的通病。
- **正确替代**：`.tmp` + `File.Replace` 原子写；显式**世代号**（不是只有 `schema` 字符串）；**读侧做新鲜度校验**。旧项目唯一的正例是 `SNAPSHOT_STALE_SECONDS = 150`（`ai_planner.py:533`）—— 审计评定为**全项目唯一真正生效的时效防护**，应该被推广到两侧，而不是只留在 Python 一侧。

### 5.9 ❌ 把"被丢弃"与"已完成"压进同一个桶（缺陷 D1）

- 见 §5.2。补充：`AiNoteSkipped` 与 `AiNoteResult` **都**递增 `_aiPlanFinished`（`ModEntry.Ai.cs:540` vs `:565`），达 `_aiPlanQueued` 即 `AiFinishPlan()`（`:543-544`、`:568-569`），而无条件刷新 `finished_at`（`:491`）。
- **正确替代**：`ai_result.json` 必须显式区分 `no-op` / `blocked` / `failed` / `done`；**只有 `done>0` 或世界状态指纹变化才算"跑完"**；否则应退避/上报而非重规划。

### 5.10 ❌ 一次性探针、无输出、无文档

- **它是什么**：26 个探针里**只有 5 个留下实际输出**（Probe8/9/10/11/13）。其余 21 个（`Probe`、`Probe2`~`Probe7`、`Probe12`、`Probe14`~`Probe26`）**只有源码没有输出**，价值未被证明也无法复现。
- **为什么绝不能重做**：探针的价值**完全在输出**。没有落盘输出的探针 = 一次性脚本 + 一个无法验证的假设，还会被后来者（包括 AI）误当成已验证事实。审计 §4.1 特别点名：`Probe26.cs:25-30` 的方法名清单是**代码里写死的字符串**，属于"作者认为存在"，**不是"已验证存在"**。
- **正确替代**：**探针产物必须入库**（输出文件 + 用途 README + 运行命令），并且把这类探针**常态化**（每次游戏更新跑一遍）。`Probe26` 的 IL 反汇编器本体（`Probe26.cs:23-100`）是全项目最值得带走的技术资产 —— 它把"猜字段语义"换成了"读 IL"。

## 6. 一句话总结：新项目的三条不可谈判原则

1. **只保留一个决策源，只保留一份契约**（§5.6、§5.7）。被禁用的能力物理删除；schema 用文件定义并两端强校验，漂移即 Error。
2. **进度与结果必须有区分度，判据来自硬事实**（§5.2、§5.3、§5.9）。绝不用"容器非空""计划已处理完"这类代理量回答"我是否在推进"。
3. **移动/可达性、地点拓扑必须是一等抽象，禁止静默兜底**（§5.4、§5.5）。取不到就报错，绝不用硬编码坐标或 `catch {}` 让缺陷隐身。
