# 00 · 开发日志

> **本文件是项目的开发过程记录，要求持续追加、永不删除历史条目。**
> 目的：让任何人（包括未来的 AI 会话）能在不读全部代码的情况下，知道"现在到哪一步、为什么这么做、踩过什么坑、下一步干什么"。

---

## 写日志的规则

1. **倒序排列：最新条目在最上面**（读者第一眼看到最新进展）。
2. 每完成一个"有意义的工作单元"就追加一条，不要攒着写。合并成一条也行，但必须写清做了哪些事。
3. 每条必须包含固定字段：`日期 / 阶段 / 目标 / 做了什么 / 结论与证据 / 下一步 / 待决`。
4. **结论必须有证据**：文件路径、行号、命令输出、日志片段。禁止只有形容词（"优化了性能"）而没有数字/证据。
5. **踩坑必写**：报错原文、根因、最终解法。同类坑第二次出现时必须引用第一次的条目编号。
6. 结构性变更（架构、协议、目录、技术栈）必须同步更新 `01-架构设计.md`，并在日志里写"已同步 01"。
7. 待决问题一旦被用户拍板，回到原条目补一行 `【已决】…`，不要改写原结论。

### 条目模板
```markdown
## YYYY-MM-DD · 条目 NNN · 阶段 PX · 一句话标题
- **目标**：这次想达成什么
- **做了什么**：动作清单（谁做的、用什么命令/文件）
- **结论与证据**：可验证的事实 + 路径/行号/输出
- **下一步**：紧接着要做的
- **待决**：需要用户拍板或外部条件的事项
```

**✅ 失焦诊断字段完美生效**（这是本轮最有价值的可观测性）
```
把焦点抢到浏览器后：windowActive=False, canMove=True, hasController=False, worldAdvancing=True
```

→ 脑现在能**精确归因**："角色不动"是 `windowActive=false` 造成的，而不是寻路出错、也不是被控制器占住。以前只能靠猜。

**🔴 严重事故：`dismiss_modal` 关掉了弹窗，却让游戏进入"半卡死"**
- 复现：角色走到床边 → 弹出 `Go to sleep for the night?` → 调 `dismiss_modal`
- 返回：`ok`，reason 写明 `选“No”（按键确认未生效，已退回 exitThisMenu 关闭）`
- **但之后**：时钟冻结在 640、`isModal=false`、`canMove=false`、世界 45 秒未推进；**用户报告"无法控制角色行动"**，画面看起来完全正常。
- 根因判定：`ConfirmByKey()` 里那两次 `receiveKeyPress(Enter/Space)` **很可能真的确认了 Yes**，游戏随即启动睡觉流程（`CanMove=false`、时间暂停）；紧接着代码又用 `exitThisMenu()` 把对话框抽走 ⇒ **流程卡在半途**。
- 这是无人值守最怕的失败形态：**画面正常、日志说 ok、实际永久停摆**。若发生在无人值守时，整晚就废了。

**🔴 家具检查是死代码 + 命中范围不足（两个 bug 叠在一起）**
1. `Skills.cs` 先判 `if (!SafeStandable(...))` 返回通用 `unreachable`，而 `SafeStandable` 发现家具时返回 false 并输出家具引用 ⇒ 后面那段"该格有家具"的分支**永远到不了**。真机表现：`move_to(9,8)` 报的是通用"被建筑/水面/障碍占据"。
2. 家具判定只比对 `f.TileLocation`，但**床是多格家具**：`move_to(10,9)` 通过了检查、成功走到该格、**并触发了睡觉弹窗**。这就是上面事故的入口。

**🟡 版本号写死**：`BridgeHost.cs:26` 是 `const string ModVersion = "0.1.0"`，而 manifest 已升 0.2.0 ⇒ 日志/`bridge.json`/health 全都报 0.1.0。这种"自称版本与实际不符"正是旧项目文档漂移的同类问题，必须修（改为从 manifest 读）。

### 三条教训（已写入架构与协议）
1. **"模态已关闭" ≠ "世界已恢复"**。成功判据必须是 `CanMove==true && Context.IsPlayerFree==true`，因此 `exec` 响应新增 `worldResumed` 字段；`worldResumed=false` 时绝不允许报成普通成功。
2. **提问类对话框禁止按确认键**（Enter/Space）。正确做法是走游戏自己的应答入口 `Game1.currentLocation.answerDialogueAction(responseKey, null)`（编译期实证可用）——它等价于"点击某个选项"，而不是"盲按键盘"。
3. **对多格物体（家具）必须用像素包围盒判定**，不能只看锚点格。

### 下一步
修复迭代 3（子代理进行中）：删除按键确认路径、改用 `answerDialogueAction`、新增 `worldResumed` 与 `isInBed/paused/shouldTimePass` 诊断字段、家具改包围盒判定、修分支顺序、版本号改从 manifest 读；快照 schema 升 `agentfarm-world/3`。

## 2026-10-11 · 条目 011 · 阶段 P2 · 第一次真机测试：8 个发现，其中 1 个改变了无人值守的可行性判断

### 目标
在真实游戏里验收里程碑 A（看得见 + 走得动），把"能跑"从自述变成证据。

### 做了什么
用户启动 SMAPI + 载入 Wahaha 存档后，我在另一侧跑完整套验收：`doctor` → `observe` → `move`（同地点 / 跨地点 / 负坐标 / 未知技能 / 超时 / 并发）→ 焦点实验 → 轨迹采样。共 40+ 次真实请求。

### 结论与证据

**✅ 通过的部分**
| 验收项 | 结果 |
|---|---|
| Mod 加载 | `AgentFarm Bridge v0.1.0 已就绪`，端口 17890，无红字 |
| bridge.json | 8 字段齐全，token 32 位十六进制 |
| `doctor` | 全绿：health / observe / 鉴权 / exec 链路 |
| `noop` | ok，0ms |
| `move_to` 同地点 | **前台条件下 100% 成功**（216~666ms/次），且每次都**重新观测确认到达** |
| 跨地点目标 | `precondition_failed`，reason 写明"跨地点移动尚未实现"+ 地点尺寸 12x12 |
| 负坐标 | `precondition_failed` |
| 未知技能 | `unknown_skill` |
| 并发 exec | 第二个返回 `busy` ✔（一次一件事） |
| **超时清理** | `move 2 10 --timeout-ms 500` → `timeout`（剩余 7 步），角色停在 (6,10)，**1.5 秒后仍在原地** ⇒ 控制器确实被清掉，没有把角色拖着走 |
| 不可达 | A* 无解 → `unreachable`，不空等 |
| 世界推进 | 时钟 630→640（8 秒），`worldAdvancing=true` |

**🔴 发现 1（最重要）：游戏失焦时，`PathFindController` 不驱动角色。**
- 失焦状态下连续 10 次 `move_to` **全部失败**，角色坐标在 6.6 秒内**一个格子都没动**（轨迹采样去重后只有一个点）；
- 把游戏拉回前台后，同样 5 次**全部成功**（216~233ms/次）；
- 但**世界时间在失焦时照常推进**（这解释了为什么"看起来在跑，其实角色没动"）。

→ 结论：**执行动作前必须让游戏窗口处于前台**。这不违反决策 D4（只动 Windows 窗口焦点，不碰游戏状态）。
→ 已实现 `brain/agentfarm/winfocus.py`（ctypes 调 `AttachThreadInput` + `SetForegroundWindow`），并做成 `agentfarm focus` 命令；`agentfarm move` 会**自动先拉前台**。
→ 闭环验证：程序化把焦点抢到浏览器（游戏失焦）→ `focus` 拉回 → `move` 两次成功，(2,10)→(5,10)→(8,10) ✔

**🔴 发现 2：意外弹窗会让游戏永久停摆，而脑看不到弹窗内容。**
角色走到床边 → 游戏弹出 `go to sleep for the night?`（Yes/No）→ **游戏时间被冻结**（`secondsSinceClockMoved=15.4s`），此后所有动作都被 `ui_modal` 拒绝。
- 这是"模态处理必须是一等公民"的第一份实机证据；
- 当时脑只能看到 `activeMenu: "DialogueBox"` 一个类名，**无法判断该关还是该答** → 新增 `ui.activeMenuText` / `dialogueResponses` / `dialogueIsQuestion`；
- 并新增技能 `dismiss_modal`：**问题型对话框永远选"否/取消"**（绝不自动选 Yes —— 那会直接结束当天），找不到"否"就按星露谷惯例选最后一项。
- 另一面：这个弹窗**意外证实了架构 §5.5 的假设 —— 打开菜单确实会暂停单人游戏时间**，P3"慢脑思考时暂停时间"的方案可行。

**🔴 发现 3：农场统计的 `weeds` / `twigs` 恒为 0（分类 bug）。**
`FarmScan.cs` 用 `ItemId == "Weeds"` 比较，而 1.6 的 `ItemId` 是数字字符串。对照真值表：
| 项 | 真值（旧数据，同存档同地块） | 我们的读数 | 判定 |
|---|---|---|---|
| stones | 241 | **241** ✔ | 对 |
| trees | 148 | **148** ✔ | 对 |
| grass | 458 | **458** ✔ | 对 |
| weeds | 443 | **0** ✘ | 分类错 |
| twigs | 114 | **0** ✘ | 分类错 |
→ 修法：改用 `obj.IsWeeds()` / `obj.IsTwig()` / `obj.IsBreakableStone()`（**都是方法**，`IsStone` 不存在）。这三个是编译期实证的。

**🔴 发现 4：`clock.weather` 恒为空串。**
1.6.15 没有 `Game1.weather`。改用 `Game1.IsRainingHere/IsSnowingHere/IsLightningHere/IsDebrisWeatherHere` 组合判定。

**🟡 发现 5：`location.isFarm` 对 FarmHouse 也返回 true。**
根因是用了 SMAPI 的 `GameLocation.IsFarm`（它对 `Farm` 与 `FarmHouse` 都返回 true）。脑若据此判断"我在农场外面"会做错决策。新增 `isOutdoorFarm`。

**🟡 发现 6：`ui.dialogsOnScreen` 恒为 4。**
它其实是 `Game1.onScreenMenus.Count`（常驻 HUD），与对话框无关。改名为 `onScreenMenus`，避免误用。

**🟡 发现 7：家具格会被当成可走目标。**
移动到屋子四角一律 `unreachable`（A* 无解），因为这些格上有家具。应当**前置拒绝**并给出精确原因，而不是让脑以为"路被围住了"。

**🟡 发现 8（未解释，待查）：体力从 270 掉到 266。**
期间只发生过移动与用户手动 WASD，理论上走路不耗体力。先记下来，不排除是用户按到了工具键。

**操作失误（记录以免重犯）**：我第一次跑 `build.ps1` 时用 `... | Select-Object -First 12` 截断输出，**`Select-Object -First N` 会掐断上游管线**，把安装脚本打断在半途，害我以为安装失败。跑会改状态的外部脚本时不要截断其输出。

  - `src\AutoFarmWorker\ModEntry.cs:643` → `this.DiscardTask("跨地点退避中");`
  - `src\AutoFarmWorker\ModEntry.cs:1110` → 同上（发起跨地点移动的入口）
  - `src\AutoFarmWorker\ModEntry.cs:1144-1145` → `在 {cur} 没找到通往 {target} 的出口，跳过这条跨地点任务` → `DiscardTask(...)`
- 结果是**全量静默跳过**：`ai_result.json` = `{"done":0,"skipped":39,"failed":0}`，39 条明细理由全是"跨地点退避中"。失败计数为 **0**。
- 旧代码作者自己已经察觉到反馈环缺失却没修：`src\AutoFarmWorker\ModEntry.cs:652-656` 注释原文——"跨地点放弃被当成干成了一件事 —— 什么都没做，看门狗却…"。
- 规划器侧同样脱节：`planner.log` 持续输出 `等待：事实快照已过期 1397s（游戏没在运行？）`；`ai_directive.json` 的 `issued_at`(16:11:10) 与 `plan_basis`(16:10:44) 不一致，计划下发时依据的世界已过期。
- 世界真值（`live_snapshot.json`）：玩家在 **FarmHouse** `[2,11]`，农场有 **798 个障碍物**、**0 格耕地**，金钱 482g。旧方案因此反复规划"在屋外南侧连片清障+锄地"——而它连屋都出不去。

**B. 由此确认的 4 个架构级缺陷（非 bug 级）**
1. **开放环**：执行结果（尤其"不可达/前置不满足"）不回流到规划器，规划器下一轮产出几乎相同的计划 → 6 天空转。
2. **LLM 直接产出坐标级动作**：绕过可达性与前置条件校验，一次 39 条，一条不可达就整批报废。
3. **失败被静默吞掉**：没有"进展=0 就必须改变行为"的进度契约；`failed:0` 掩盖了 100% 失败。
4. **缺少任务/技能抽象**：用 `Watchdog / Blacklist / Fallback / AutoRescue / TeleportFallback / CrossLocationMode / MaxTaskRetries=40` 等 10+ 个兜底旋钮去补结构性缺口。

**C. 遗留运行态风险**
- 旧规划器守护进程**仍在运行**：PID **9268**（pythonw `ai_planner.py --watch --poll 15`），启动于 2026-10-05 03:01:37，已跑 6 天+。游戏一启动它就会重新写指令文件，**与新系统抢控制权**。
- 旧 `AutoFarmWorker` 配置为 `AutoStart=true` + `AiDirectiveEnabled=true`，游戏启动即自启。
