# 00 · 开发日志

> **本文件是项目的开发过程记录，要求持续追加、永不删除历史条目。**
> 目的：让任何人（包括未来的 AI 会话）能在不读全部代码的情况下，知道"现在到哪一步、为什么这么做、踩过什么坑、下一步干什么"。

---

## 写日志的规则

1. **倒序排列：最新条目在最上面**（读者第一眼看到最新进展）。
2. 每完成一个"有意义的工作单元"就追加一条，不要攒着写。合并成一条也行，但必须写清做了哪些事。
3. 每条必须包含固定字段：`日期 / 阶段 / 目标 / 做了什么 / 结论与证据 / 下一步 / 待决`。
4. **结论必须有证据**：文件路径、行号、命令输出、日志片段。禁止只有形容词（"优化了性能"）而没有数字/证据。
5. **踩坑必写**：报错原文、根因、最终解法。同类坑第二次出现时必须引用第一次的条目编号。
6. 结构性变更（架构、协议、目录、技术栈）必须同步更新 `01-架构设计.md`，并在日志里写"已同步 01"。
7. 待决问题一旦被用户拍板，回到原条目补一行 `【已决】…`，不要改写原结论。

### 条目模板
```markdown
## YYYY-MM-DD · 条目 NNN · 阶段 PX · 一句话标题
- **目标**：这次想达成什么
- **做了什么**：动作清单（谁做的、用什么命令/文件）
- **结论与证据**：可验证的事实 + 路径/行号/输出
- **下一步**：紧接着要做的
- **待决**：需要用户拍板或外部条件的事项
```

## 2026-10-11 · 条目 017 · 阶段 P2 · IL 探针的**静默漏打** bug：以前所有"读 IL 得出的结论"都要重打一遍

### 目标
查清一件怪事：IL dump 里偏移**不连续**（`IL_0000` 直接跳到 `IL_0008`，中间少了 3 字节），而 `TryReadSaveFile` 的路径拼接结论就卡在这几个字节上。

### 做了什么
- 改 `tools\il-probe\Probe26.cs`：
  1. **修掉静默漏打**：原版最后一行是 `if (!string.IsNullOrEmpty(operand)) Console.WriteLine(...)`，于是**所有没有操作数的指令**（`ldarg.0/1`、`ldloc`、`stloc`、`ret`、`add`、`pop`、`br`… 即 `OperandType.InlineNone`）全被悄悄丢掉。改成一律打印；
  2. 目标列表支持命令行传入 `Type|Method`（不必改代码重编译）；
  3. 支持 dump **编译器生成的嵌套类型**：`Outer+NestedSubstring|Method`；

  5. 游戏目录回退顺序：命令行参数 > 环境变量 `STARDEW_GAME_DIR` > 旧机器硬编码路径。
- 用修好的探针**重打**了三个关键方法并复核结论。

### 结论与证据
- `Farmer.Halt()`（重打后）：`if (FarmerSprite.PauseForSingleAnimation || isRidingHorse() || UsingTool) skip base.Halt()` → **无条件** `movementDirections.Clear()` → 条件 `stopJittering()` → `armOffset = Vector2.Zero` → 骑马时 `mount.Halt()` → `IsSitting()` 时 `ShowSitting()` → `ret`。**全程没有 `CanMove = false`，没有提前返回**（条目 016 的修复依据因此成立）。
- `GameLocation.isCollidingWithWarp(Rectangle, Character)`：`if (ignoreWarps) return null;` → 遍历 `warps` → `if (character is NPC || !w.npcOnly.Value)` → `w.X == Floor(position.Left/64.0) || w.X == Floor(position.Right/64.0)` 且 `w.Y == Floor(position.Top/64.0) || w.Y == Floor(position.Bottom/64.0)`。**证实 `warp.X/Y` 是"玩家矩形边缘要碰到的格"（源格），不是"要站上去的格"**。
- `SaveGame.TryReadSaveFile(String file, String fileNameSuffix, String& error)`：`Path.Combine(GetSavesFolder(), file, file + fileNameSuffix)` → `File.Exists`（失败再加 `.xml`）→ 不存在则 `FileDoesNotExist(out error); return null;`。⇒ **`SaveGame.Load(存档文件夹名)` 是对的**（文件布局 `Saves\<名字>\<名字>`），且**文件不存在不会抛异常**，只会把错误状态交给加载界面。
- `SaveGame.Load(String filename)`：`Game1.gameMode = 6` → 设置加载提示文案 → `Game1.currentLoader = getLoadEnumerator(filename)`。这一步就是条目 016 里 `load_save` 技能的全部实现依据。

### 教训
> 探针本身也是代码，也会有 bug，而且**它会静静地骗你**。凡是"IL 里没看到某条指令，所以断言它不存在"的结论，都必须先确认探针**没有把这类指令丢掉**。本条目之后，"看不到 `ret`"这类否定性结论才算可信。

## 2026-10-11 · 条目 014 · 阶段 P2 · 修复迭代 3：卡死根因被 IL 推翻重写，Mod v0.3.0 装机

### 目标
修掉 `dismiss_modal` 导致的"半卡死"事故，外加两个 bug（家具死代码、版本号写死）。

### 结论与证据

**🔴 我的假设是错的，子代理用 IL 反汇编给出了真正的根因**
我当时的判定是"`Enter/Space` 真的确认了 Yes，游戏启动睡觉流程，然后 exitThisMenu 把对话框抽走导致卡在半途"。
**IL 实证推翻了它 —— 根本不需要按到任何确认键就会卡死**：
```
1) 游戏弹出提问框（Game1.drawObjectQuestionDialogue）时自己就置 CanMove=false
2) DialogueBox.receiveKeyPress 对 Enter(13)/Space(32) 没有应答语义；
   若该键命中 Options.actionButton，会被转成 receiveLeftClick(0,0,true)＝"确认当前选中项"
3) 兜底的 exitThisMenu() → cleanupBeforeExit() 是**空方法**：
   既不复位 Game1.dialogueUp，也不复位 player.CanMove
4) Game1.shouldTimePass()：if (!player.CanMove && !player.UsingTool) return player.forceTimePass;
   ⇒ CanMove 停在 false ⇒ **时钟永久停摆**
```
→ **真正的修法是"关闭路径必须走 `closeDialogue()`"**（它会复位 `dialogueUp` 与 `CanMove`），`exitThisMenu()` 只能当最后兜底。子代理相对任务书擅自加的这一处"行为加强"是**对的**，否则事故会原样复现。
→ 教训：**"根因看起来合理"不等于"根因正确"**。我基于现象编了一个自洽的故事（按了 Yes），而 IL 把每一环都钉死了。以后遇到这类"游戏内部状态半途不回滚"的问题，**优先反汇编而不是编故事**。

**另一处发现：`answerDialogueAction` 收的是组合键**
游戏自身走 `GameLocation.answerDialogue(Response)`，它把答案拼成 `lastQuestionKey 第一段 + "_" + responseKey`（例 `Sleep_No`）再转调 `answerDialogueAction`。**裸传 `"No"` 在 `questionKey_xxx` 型对话框上是空操作。**

**我的拍板（相对子代理的偏离）**：应答**优先用 `answerDialogue(Response)` 而不是 `answerDialogueAction`**。

### 结论与证据

**A. 旧方案的架构与停摆原因（一手证据）**
- 协议是**文件轮询**：LLM 规划器 `tools/scripts/ai_planner.py`（47 KB）每 ~20 秒写 `AutoFarmWorker\data\ai_directive.json`（schema `stardew-ai-directive/2`，内容是 **39 条 `{id, action, xy}` 坐标级动作**），Mod 读文件执行后写 `ai_result.json`。
- 执行器在"人不在目标地点"时直接丢弃整批任务：
  - `src\AutoFarmWorker\ModEntry.cs:643` → `this.DiscardTask("跨地点退避中");`
  - `src\AutoFarmWorker\ModEntry.cs:1110` → 同上（发起跨地点移动的入口）
  - `src\AutoFarmWorker\ModEntry.cs:1144-1145` → `在 {cur} 没找到通往 {target} 的出口，跳过这条跨地点任务` → `DiscardTask(...)`
- 结果是**全量静默跳过**：`ai_result.json` = `{"done":0,"skipped":39,"failed":0}`，39 条明细理由全是"跨地点退避中"。失败计数为 **0**。
- 旧代码作者自己已经察觉到反馈环缺失却没修：`src\AutoFarmWorker\ModEntry.cs:652-656` 注释原文——"跨地点放弃被当成干成了一件事 —— 什么都没做，看门狗却…"。
- 规划器侧同样脱节：`planner.log` 持续输出 `等待：事实快照已过期 1397s（游戏没在运行？）`；`ai_directive.json` 的 `issued_at`(16:11:10) 与 `plan_basis`(16:10:44) 不一致，计划下发时依据的世界已过期。
- 世界真值（`live_snapshot.json`）：玩家在 **FarmHouse** `[2,11]`，农场有 **798 个障碍物**、**0 格耕地**，金钱 482g。旧方案因此反复规划"在屋外南侧连片清障+锄地"——而它连屋都出不去。

**B. 由此确认的 4 个架构级缺陷（非 bug 级）**
1. **开放环**：执行结果（尤其"不可达/前置不满足"）不回流到规划器，规划器下一轮产出几乎相同的计划 → 6 天空转。
2. **LLM 直接产出坐标级动作**：绕过可达性与前置条件校验，一次 39 条，一条不可达就整批报废。
3. **失败被静默吞掉**：没有"进展=0 就必须改变行为"的进度契约；`failed:0` 掩盖了 100% 失败。
4. **缺少任务/技能抽象**：用 `Watchdog / Blacklist / Fallback / AutoRescue / TeleportFallback / CrossLocationMode / MaxTaskRetries=40` 等 10+ 个兜底旋钮去补结构性缺口。

**C. 遗留运行态风险**
- 旧规划器守护进程**仍在运行**：PID **9268**（pythonw `ai_planner.py --watch --poll 15`），启动于 2026-10-05 03:01:37，已跑 6 天+。游戏一启动它就会重新写指令文件，**与新系统抢控制权**。
- 旧 `AutoFarmWorker` 配置为 `AutoStart=true` + `AiDirectiveEnabled=true`，游戏启动即自启。

**D. 可复用资产（初步）**
- 知识：26 个 Probe 逆向探针的实测结论、`docs/ARCHITECTURE.md`(13.8 KB)、`docs/COMMANDS.md`(23 KB)、`docs/WATCHDOG_AND_AI.md`(14.6 KB)、1.6.15 API 踩坑。
  - **【更正 2026-10-11，见条目 004】** 26 个探针中**只有 5 个**（Probe8/9/10/11/13）留下实测输出，其余 21 个只有源码 = **未验证假设**，不可当结论使用。
- 数据：`crop_economics.json`(11 KB)、`farm_tiles.json`(244 KB 动作池样本)。
- 运维：`build.ps1`（编译+备份+安装 mod 到游戏目录）、`SaveBackup`/`Automate` 第三方 mod。
- 不可复用：旧的**协议**（文件轮询 + 坐标动作清单）与**执行模型**（批量丢弃），必须重做。
